# 毕节生活地图 - 项目总结

## 一句话描述
一个基于微信小程序的本地生活地图应用，聚合地点信息、支持用户共创、积分激励与管理员审核的完整闭环系统。

---

## 项目核心亮点

### 1. 完整的产品架构设计
- **前端**：Vue3 组合式 API + uni-app 跨端框架
- **后端**：uniCloud 云开发（云对象 + 云函数 + 云数据库 + 云存储）
- **核心功能**：地图展示、搜索、投稿审核、积分体系、评论评分、用户收藏

### 2. 用户共创闭环系统
实现了从投稿 → 审核 → 发布 → 积分激励的完整流程：
- 用户可补充新地点（获 10 分）或纠错反馈（获 5 分）
- 投稿默认待审核（pending），管理员通过/驳回/撤销驳回
- 通过即刻获得积分，用户可实时查看共创记录与积分统计

### 3. 权限管理与安全机制
- **权限分层**：游客 / 普通用户 / 管理员三级权限体系
- **Token 认证**：HMAC-SHA256 签名，7 天有效期，支持自动刷新
- **White-list 管理**：管理员白名单 + bootstrap 流程（首用户自动为管理）
- **数据隐私**：关键表关闭客户端直连，仅云函数访问

### 4. 数据一致性与性能优化
- **反范式化存储**：地点表冗余评分数据，避免频繁关联查询
- **后端排序/搜索**：支持距离排序（Haversine 公式）、评分排序、模糊搜索
- **索引策略**：name、status、create_date、contributor_openid 等关键字段索引
- **分页机制**：20 条/页，支持自定义分页大小

### 5. 交互体验优化
- **地图交互**：拖拽面板、地点详情半屏/全屏切换、"回到我的位置"快速定位
- **搜索体验**：搜索历史 + 删除历史，后端模糊匹配
- **图片处理**：前端自动压缩，支持多图上传与预览
- **实时数据**：距离计算实时更新，评论评分即刻聚合

## 核心功能模块详解

### 1. 地图页面（pages/map/map.vue）- 核心功能页
- **地图展示**：全屏地图 + 用户定位 + 标记点聚合
- **多维度搜索**：关键字搜索（后端模糊匹配）+ 分类筛选（全部/美食/景点/厕所/商店/其他）
- **排序功能**：距离排序、评分排序、综合排序
- **地点详情**：两个标签页
  - 概览：图片预览、地址、坐标、贡献者、一键导航、收藏按钮
  - 简介：展示通过审核的所有评论
- **拖拽面板**：可拖拽的列表面板，支持半屏↔全屏切换

### 2. 地点管理页（pages/admin/spots.vue）- 仅管理员
- **列表管理**：展示所有地点，支持多维度筛选
  - 分类筛选 / 审核状态筛选 / 来源筛选 / 名称搜索
- **新增地点**：
  - 方式一：关键字搜索 POI（调用腾讯地图），一键填充
  - 方式二：地图选点工具（自建选点页）
  - 自动压缩图片上传（最多 9 张）
- **编辑地点**：修改任何字段，自动记录修改者与时间
- **删除地点**：二次确认 + 级联删除关联数据

### 3. 审核管理页（pages/admin/review.vue）- 仅管理员
- **投稿列表**：展示所有待审核投稿（新增地点 + 纠错反馈）
- **审核操作**：
  - 通过：发布地点 + 用户获得积分
  - 驳回：填写原因 + 用户可见
  - 撤销驳回：恢复为待审核
- **投稿详情**：原地点信息、投稿说明、证明图片、联系方式

### 4. 用户共创页（pages/contributions/contributions.vue）
- **共创记录**：展示用户所有投稿（新增/纠错）及审核状态
- **积分统计**：总积分 + 每条记录的积分值
- **详情查看**：投稿内容 + 审核结果 + 驳回原因（如有）
- **实时更新**：通过投稿即刻显示积分

### 5. 补充/纠错页（pages/contribute/contribute.vue）
- **补充新地点**：
  - 必填：类型、名称、地址、经纬度
  - 可选：备注、图片（≤3张）、联系方式
  - 地址可手输或地图选点
- **纠错反馈**：
  - 选择要纠错的地点
  - 选择纠错类型（预设分类）
  - 填写纠错说明
  - 可选上传证明图片
- **提交流程**：验证 → 图片压缩 → 上传 → 二次确认
- **匿名投稿**：未登录用户可匿名提交

### 6. 评论评分系统
- **发表评论**：评分（1-5星） + 文字 + 配图（≤3张）
- **评论审核**：默认待审核，管理员通过后显示
- **评分聚合**：自动计算地点平均评分与评论数
- **显示位置**：地点详情"简介"标签页

### 7. 用户收藏系统
- **快速收藏**：地点详情页一键收藏
- **收藏列表**：专属页面查看所有收藏（支持搜索/筛选）
- **防重复**：组合唯一索引防止重复收藏
- **取消收藏**：长按或右滑删除

### 8. 权限与认证系统
- **微信登录**：uni.login() → 云函数换取 OpenID → 本地存储 Token
- **自动登录**：Token 有效期 7 天，期间无需重复登录
- **管理员识别**：
  - 首个用户自动为管理员（bootstrap）
  - 后续通过白名单添加
- **权限校验**：管理操作前验证 Token → 查询白名单 → 允许/拒绝

## 关键技术决策

### 1. 为什么选择 uni-app？
- 一套代码支持微信小程序、H5、App 等多端
- 官方提供地图、定位等小程序原生能力封装
- 开发效率高，学习曲线平缓

### 2. 为什么选择 uniCloud？
- 免运维：无需搭建服务器，按需计费
- 原生集成：uni-app 与 uniCloud 无缝对接
- 功能完整：云函数、云对象、云数据库、云存储、CDN 一体化
- 快速迭代：适合初创产品快速验证

### 3. 为什么采用反范式化设计？
- 评论数和评分是高频访问的统计数据，每次查询都要 join
- 反范式化存储在 spots 表中，避免频繁的关联查询
- 权衡空间与查询性能，适合本项目的数据规模

### 4. 为什么用 Token + White-list 而不是 RBAC？
- 项目初期管理员数量固定（1-5 人）
- White-list 简单直观，易于维护
- Token 可支持 7 天免登录，提升用户体验
- 后续可扩展为完整的 RBAC 系统

## 面试可能问到的问题与回答思路

### Q1: 这个项目最有难度的地方在哪里？
**A**: 权限管理与数据一致性。
- 权限方面：需要设计三级权限体系（游客/用户/管理员），实现 Token 认证 + White-list 校验 + 云函数鉴权
- 数据一致性：投稿审核涉及多表联动（投稿 → 地点 → 用户积分），需要确保原子性；评论评分需要实时更新地点的平均评分

### Q2: 积分系统是如何实现的？
**A**: 
- 投稿通过审核时，云函数自动计算积分值（新增 10 分、纠错 5 分）
- 在 `review` 方法中执行：更新投稿状态 + 用户表 points 字段累加
- 用户通过 `getContributions` 接口查询共创记录时，同时返回总积分
- 前端"我的共创"页面实时展示积分变化

### Q3: 如何处理搜索性能？
**A**:
- 数据库层面：在 `name` 字段建立索引，支持模糊查询
- 后端处理：使用 MongoDB 正则表达式或全文索引进行模糊匹配
- 分页机制：20 条/页，减少单次查询数据量
- 前端缓存：简单使用 localStorage 缓存搜索历史

### Q4: 如何保证权限安全？
**A**:
- 微信登录：使用微信 jscode2session 接口换取 OpenID，防止伪造
- Token 签名：使用 HMAC-SHA256，加入时间戳防重放
- 云函数鉴权：每个需要权限的接口都验证 Token，并查询 White-list
- 数据表权限：关键表（users、admin-whitelist）关闭客户端直连

### Q5: 为什么用 uni-app 而不是原生微信小程序？
**A**:
- 代码复用：一套代码支持微信小程序、H5、App
- 开发效率：Vue 语法更熟悉，开发速度快
- 工具链完整：官方提供地图、定位、文件上传等原生能力封装
- 社区活跃：官方支持完善，问题易解决

### Q6: uniCloud 相比自建后端有什么优势/劣势？
**A**:
- **优势**：
  - 免运维：自动扩容、安全防护、备份恢复
  - 快速迭代：快速上线，专注业务开发
  - 成本低：初期低成本，按需计费
  - 集成完整：云函数、云数据库、云存储、CDN 一体化
- **劣势**：
  - 定制性差：受平台限制，难以深度优化
  - 迁移成本高：代码深度绑定 uniCloud，迁移困难
  - 厂商依赖：服务稳定性依赖厂商

### Q7: 如何处理地点距离的实时计算？
**A**:
- 用户打开地图时上报经纬度
- 后端在 `getList` 接口中，对每个地点使用 Haversine 公式计算距离
- 支持按距离排序，返回给前端
- 地点卡片展示距离，并支持距离排序

### Q8: 投稿审核流程中，如何处理纠错投稿？
**A**:
- 纠错投稿保存独立记录，`report_type = 'correction'`，`target_id` 指向原地点
- 管理员通过时：
  1. 将纠错内容合并到原地点
  2. 更新原地点的修改者与修改时间
  3. 设置纠错记录状态为 approved
  4. 投稿者获得 5 分积分
- 管理员驳回时：设置状态为 rejected，记录驳回原因

### Q9: 数据库中为什么要存储 `rating_count` 和 `average_rating`？
**A**:
- 反范式化设计，避免每次查询地点时都 join 评论表计算
- 评论数和评分是高频访问的数据，经常用于排序和展示
- 每次有新评论或删除评论时，实时更新这两个字段
- 权衡空间成本与查询性能，提升用户体验

### Q10: 如何实现"撤销驳回"功能？
**A**:
- 驳回时记录原因，设置状态为 `rejected`
- 撤销驳回：仅需将状态改回 `pending`
- 不涉及原地点数据变化，操作简单
- 用户重新可以看到该投稿在"我的共创"页的状态变化
